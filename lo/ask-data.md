## ຖາມຖານຂໍ້ມູນຂອງທ່ານ, ໄດ້ຄຳຕອບທີ່ກວດສອບໄດ້

ເຊື່ອມຕໍ່ Postgres, BigQuery, Snowflake ຫຼື ClickHouse, ກຳນົດຕົວຊີ້ວັດຂອງທ່ານຄັ້ງດຽວ, ແລ້ວໃຫ້ທຸກຄົນໃນທີມຖາມດ້ວຍພາສາທຳມະດາ. ທຸກຄຳຕອບມາພ້ອມກຣາຟ, ຕາຕະລາງ ແລະ SQL ທີ່ມັນໃຊ້.

## ເຊື່ອມຕໍ່ກັບຖານຂໍ້ມູນທີ່ທ່ານໃຊ້ຢູ່ແລ້ວ

ຫົກເອັນຈິນ, ຕັ້ງແຕ່ Postgres ໃນເຊີບເວີຂອງທ່ານເອງ ຈົນເຖິງໂປຣເຈັກ BigQuery. ເລືອກປະເພດ, ວາງຂໍ້ມູນເຂົ້າສູ່ລະບົບ, ເລືອກຕາຕະລາງ — ການເຊື່ອມຕໍ່ຈະຖືກທົດສອບກ່ອນບັນທຶກ.

- **PostgreSQL** — Host, ພອດ 5432, ໂໝດ SSL
- **MySQL** — Host, ພອດ 3306, ໂໝດ SSL
- **ClickHouse** — Host, ພອດ HTTP 8123
- **Snowflake** — ບັນຊີ, warehouse ແລະ schema
- **BigQuery** — ກະແຈ service account ແລະ location
- **Redshift** — Endpoint ຂອງ cluster, ພອດ 5439

- ຂໍ້ມູນເຂົ້າສູ່ລະບົບຖືກເຂົ້າລະຫັດເມື່ອເກັບ, ບໍ່ເຄີຍສົ່ງກັບໄປຫາບຣາວເຊີ
- ໂໝດອ່ານຢ່າງດຽວ: ມີແຕ່ SELECT ເທົ່ານັ້ນທີ່ເຂົ້າເຖິງໄດ້
- ສ້າງແບບຈຳລອງສະເພາະຕາຕະລາງທີ່ທ່ານເລືອກ

## ຈາກ connection string ສູ່ບອດ

ການສ້າງໂມເດວເປັນຮ່າງທຳອິດທີ່ທ່ານແກ້ໄຂ, ບໍ່ແມ່ນໂຄງການທີ່ຕ້ອງວາງແຜນ.

1. **ເຊື່ອມຕໍ່ຖານຂໍ້ມູນ** — ຊີ້ໄປທີ່ PostgreSQL, MySQL, Redshift, ClickHouse, Snowflake ຫຼື BigQuery. ຂໍ້ມູນເຂົ້າສູ່ລະບົບຖືກເຂົ້າລະຫັດຂະນະຈັດເກັບ, ແລະ ສາມາດໝາຍການເຊື່ອມຕໍ່ເປັນອ່ານຢ່າງດຽວ ເພື່ອບໍ່ໃຫ້ມີຫຍັງນອກຈາກ SELECT ເຂົ້າເຖິງມັນ.
2. **ປັບແຕ່ງໂມເດວ** — ລະບົບອ່ານໂຄງສ້າງ schema ແລະ ສ້າງ cube, ການ join ແລະ ຕົວຊີ້ວັດຮອບທຳອິດໃຫ້. ເຊື່ອງສິ່ງທີ່ບໍ່ຄວນມີໃຜສືບຄົ້ນ, ປ່ຽນຊື່ສິ່ງທີ່ມີແຕ່ຜູ້ສ້າງເຂົ້າໃຈ, ແລະ ເພີ່ມຕົວຊີ້ວັດທີ່ທຸລະກິດຂອງທ່ານລາຍງານແທ້.
3. **ຖາມ, ແລ້ວປັກໝຸດ** — ຖາມດ້ວຍພາສາທຳມະດາ, ກວດ SQL ເບື້ອງຫຼັງຄຳຕອບ, ແລ້ວປັກໝຸດຄຳຕອບທີ່ຄວນເກັບໄວ້ ໃສ່ບອດທີ່ທີມຂອງທ່ານເປີດທຸກເຊົ້າ.

## ການວິເຄາະແບບບໍລິການຕົນເອງ ທີ່ບໍ່ແຕ່ງຕົວເລກຂຶ້ນເອງ

ມີຊັ້ນເຊິງຄວາມໝາຍຢູ່ລຸ່ມຄຳຖາມ, ຄຳຕອບຈຶ່ງສອດຄ່ອງກັນ.

### ຖາມດ້ວຍພາສາທຳມະດາ

ພິມຄຳຖາມຄືກັບທີ່ທ່ານຖາມເພື່ອນຮ່ວມງານ. ຄຳຕອບກັບມາເປັນຕາຕະລາງ ແລະ ກຣາຟທີ່ເໝາະກັບຮູບແບບຂອງຜົນ — ພ້ອມຄຳສັ່ງທີ່ມັນໃຊ້, ໃຜກໍກວດວິທີຄິດໄດ້.

### ໂມເດວເຊິງຄວາມໝາຍ ບໍ່ແມ່ນການເດົາ

ຕົວຊີ້ວັດ, ມິຕິ ແລະ ການ join ກຳນົດຄັ້ງດຽວ ແລະ ຄອມໄພລ໌ເຂົ້າທຸກຄຳສັ່ງ. ລາຍຮັບມີຄວາມໝາຍດຽວກັນໃນທຸກຄຳຕອບ, ແລະ ຄຳຖາມທີ່ໂມເດວສະແດງບໍ່ໄດ້ ຈະບໍ່ກາຍເປັນການ join ທີ່ຫຼອນຂຶ້ນມາແບບງຽບໆ.

### ຄຳຖາມທີ່ຢືນຢັນແລ້ວ ຖືກຕ້ອງຕະຫຼອດ

ບັນທຶກຄຳຕອບທີ່ທ່ານກວດແລ້ວເປັນຕົວຢ່າງທີ່ຢັ້ງຢືນແລ້ວ. ຄຳຖາມ ແລະ SQL ຂອງມັນຈະເຂົ້າໄປຢູ່ໃນຕົວຢ່າງທີ່ໂມເດວອ່ານກ່ອນຂຽນຄຳສອບຖາມ, ດັ່ງນັ້ນຄຳຖາມທີ່ຄ້າຍກັນຄັ້ງຕໍ່ໄປຈະເຮັດຕາມແບບທີ່ທ່ານອະນຸມັດ.

### ບອດ ທີ່ສ້າງຈາກຄຳຕອບ

ປັກໝຸດຄຳຕອບໃດກໍໄດ້ໃສ່ບອດ. ບອດມີຫຼາຍແທັບ, ຕົວກັ່ນຕອງຮ່ວມ ແລະ ຊ່ວງວັນທີທີ່ເປັນແບບສຳພັດສະເໝີ — ບອດທີ່ບັນທຶກເປັນ “7 ວັນຫຼ້າສຸດ” ເດືອນໜ້າກໍຍັງໝາຍເຖິງ 7 ວັນຫຼ້າສຸດ.

### SQL Lab ສຳລັບສ່ວນທີ່ເຫຼືອ

ບາງຄຳຖາມພິມເອງໄວກວ່າອະທິບາຍ. ຂຽນ SQL ເອງເທິງໂມເດວເຊິງຄວາມໝາຍດຽວກັນ, ບັນທຶກຄຳສອບຖາມທີ່ໃຊ້ຊ້ຳ, ສ້າງກຣາຟຈາກຜົນລັບ ແລະ ປັກໝຸດໃສ່ບອດ.

### ແບ່ງປັນຕົວເລກ ບໍ່ແມ່ນຂໍ້ມູນເຂົ້າລະບົບ

ບອດທີ່ແບ່ງປັນ ສະແດງຕົວເລກໂດຍບໍ່ມອບຖານຂໍ້ມູນເບື້ອງຫຼັງໃຫ້. ສິດເຂົ້າເຖິງກຳນົດຕໍ່ແຫຼ່ງຂໍ້ມູນ, ແລະ ຜູ້ເບິ່ງໄດ້ບອດ ບໍ່ແມ່ນໜ້າຈໍສືບຄົ້ນ.

## ເຊື່ອມຕໍ່ກັບຫຍັງ ແລະ ທ່ານໄດ້ຫຍັງ

ທຸກສິ່ງທີ່ຊັ້ນໂມເດວ, ບອດ ແລະ ໜ້າຈໍ SQL ຮອງຮັບແທ້.

### ຖານຂໍ້ມູນ ແລະ ຄັງຂໍ້ມູນ

- PostgreSQL ແລະ MySQL
- Redshift ແລະ ClickHouse
- Snowflake ແລະ BigQuery
- ເລືອກຕາຕະລາງຕອນເຊື່ອມຕໍ່ — ໂມເດວອ່ານສະເພາະຕາຕະລາງເຫຼົ່ານັ້ນ

### ຊັ້ນເຊິງຄວາມໝາຍ

- cube ສ້າງຈາກ schema ຂອງທ່ານ, ແລ້ວປັບແຕ່ງ
- ຕົວຊີ້ວັດ ແລະ ມິຕິຄຳນວນທີ່ທ່ານກຳນົດ
- ການ join ແນະນຳຈາກຄີ, ຢືນຢັນໂດຍທ່ານ
- cube ອະນຸພັນ ສຳລັບຮູບແບບທີ່ຂຽນດ້ວຍ SQL ຢ່າງດຽວແລ້ວຊັບຊ້ອນ
- ບໍລິບົດທຸລະກິດ ແລະ ຄຳສັບທີ່ໂມເດວອ່ານ

### ບອດ ແລະ ກຣາຟ

- ຫຼາຍແທັບໃນບອດດຽວ
- ຊ່ວງວັນທີແບບສຳພັດ ທີ່ຍັງສຳພັດຕະຫຼອດ
- ຕົວກັ່ນຕອງລະດັບບອດ ທີ່ຍົກອອກມາຈາກທຸກແຜ່ນ
- ກຣາຟເລືອກຕາມຮູບແບບຂອງຜົນ
- ແບ່ງປັນດ້ວຍລິ້ງ, ໂດຍບໍ່ເປີດເຜີຍແຫຼ່ງຂໍ້ມູນ

### ສຳລັບຄົນທີ່ຂຽນ SQL

- SQL Lab ກັບການເຊື່ອມຕໍ່ດຽວກັນ
- ຄູ່ຄຳຖາມ ແລະ SQL ທີ່ຢືນຢັນແລ້ວ
- ຂອບເຂດຕາຕະລາງ — ສິ່ງທີ່ໂມເດວເຫັນໄດ້ ແລະ ເຫັນບໍ່ໄດ້
- ບັງຄັບຈຳກັດຈຳນວນແຖວໃນທຸກຄຳສັ່ງ
- ໂຫລດ schema ຄືນ ເມື່ອຄັງຂໍ້ມູນປ່ຽນ

### ໃຊ້ໄດ້ກັບຕົວແທນຂອງທ່ານ

- ຕົວແທນສືບຄົ້ນໂມເດວເຊິງຄວາມໝາຍດຽວກັນໄດ້
- ຄຳຕອບສົ່ງໄປທີ່ແຊັດ, ກ່ອງຂໍ້ຄວາມ ຫຼື ລາຍງານຕາມກຳນົດເວລາ
- MCP endpoint ສຳລັບລູກຂ່າຍພາຍນອກ
- ບັນທຶກຄຳຖາມ, ຄຳສັ່ງ ແລະ ຄ່າໃຊ້ຈ່າຍ ໃນແຕ່ລະຄັ້ງ

### ການຄວບຄຸມ

- ສິດເຂົ້າເຖິງກຳນົດຕໍ່ແຫຼ່ງຂໍ້ມູນ
- ການເຊື່ອມຕໍ່ແບບອ່ານຢ່າງດຽວ
- ຂໍ້ມູນເຂົ້າລະບົບເຂົ້າລະຫັດຂະນະຈັດເກັບ, ບໍ່ເຄີຍສົ່ງກັບໄປບຣາວເຊີ
- ແບ່ງປັນບອດ ໂດຍບໍ່ຕິດການເຊື່ອມຕໍ່ໄປນຳ

## ຄຳຖາມກ່ຽວກັບການຖາມຂໍ້ມູນ

ສິ່ງທີ່ທີມຂໍ້ມູນກວດ ກ່ອນເຊື່ອມມັນກັບຖານຂໍ້ມູນທີ່ໃຊ້ງານຈິງ.

### ຂ້ອຍເຊື່ອມຕໍ່ຖານຂໍ້ມູນ ແລະ ຄັງຂໍ້ມູນໃດໄດ້ແດ່?

PostgreSQL, MySQL, Redshift, ClickHouse, Snowflake ແລະ BigQuery. ສາມາດໝາຍການເຊື່ອມຕໍ່ເປັນອ່ານຢ່າງດຽວ ເພື່ອບໍ່ໃຫ້ມີຫຍັງນອກຈາກ SELECT ເຂົ້າເຖິງມັນ, ແລະ ຂໍ້ມູນເຂົ້າລະບົບຖືກເຂົ້າລະຫັດຂະນະຈັດເກັບ ແລະ ບໍ່ເຄີຍສົ່ງກັບໄປບຣາວເຊີ.

### ຕ່າງຈາກການໃຫ້ LLM ຂຽນ SQL ດິບແນວໃດ?

ໂມເດວທີ່ເດົາຊື່ຕາຕະລາງດິບ ຈະ join ຜິດສອງຖັນໂດຍບໍ່ລັງເລ ແລ້ວຍື່ນຕົວເລກທີ່ຜິດແຕ່ໝັ້ນໃຈໃຫ້ທ່ານ. ຢູ່ນີ້ ຄຳຖາມເຮັດວຽກກັບໂມເດວເຊິງຄວາມໝາຍ: ທ່ານກຳນົດຕົວຊີ້ວັດ, ມິຕິ ແລະ ການ join ຄັ້ງດຽວ, ແລະ ທຸກຄຳຕອບຄອມໄພລ໌ຈາກນິຍາມເຫຼົ່ານັ້ນ. “ລາຍຮັບ” ມີຄວາມໝາຍດຽວກັນໃນທຸກກຣາຟ, ແລະ ຄຳຖາມທີ່ສະແດງຜ່ານໂມເດວບໍ່ໄດ້ ຈະບໍ່ກາຍເປັນຄຳສັ່ງທີ່ແຕ່ງຂຶ້ນແບບງຽບໆ.

### ຕ້ອງສ້າງໂມເດວທຸກຢ່າງກ່ອນ ຈຶ່ງຈະໄດ້ຄຳຕອບບໍ?

ບໍ່ຕ້ອງ. ລະບົບອ່ານ schema ເມື່ອເຊື່ອມຕໍ່ ແລະ ສ້າງ cube, ການ join ແລະ ຕົວຊີ້ວັດຮອບທຳອິດໃຫ້ທ່ານ. ຈາກນັ້ນທ່ານປັບແຕ່ງ — ເຊື່ອງຕາຕະລາງທີ່ບໍ່ຄວນມີໃຜສືບຄົ້ນ, ປ່ຽນຊື່ຖັນທີ່ມີແຕ່ຜູ້ສ້າງເທົ່ານັ້ນເຂົ້າໃຈ, ແລະ ເພີ່ມຕົວຊີ້ວັດທີ່ທຸລະກິດຂອງທ່ານລາຍງານແທ້.

### ຍັງຂຽນ SQL ເອງໄດ້ບໍ່ ເມື່ອຈຳເປັນ?

ໄດ້. SQL Lab ແລ່ນ SQL ທີ່ທ່ານຂຽນເອງເທິງການເຊື່ອມຕໍ່ ແລະ ໂມເດວເຊິງຄວາມໝາຍດຽວກັນ — ບັນທຶກຄຳສອບຖາມທີ່ໃຊ້ຊ້ຳ, ສ້າງກຣາຟຈາກຜົນລັບແລ້ວປັກໝຸດໃສ່ບອດ, ຫຼື ປ່ຽນຄຳສອບຖາມເປັນ derived cube. ຕົວຢ່າງທີ່ຢັ້ງຢືນແລ້ວມາຈາກ ChatQL ເອງ: ບັນທຶກຄຳຕອບທີ່ທ່ານໄວ້ໃຈ, ແລ້ວຄຳຖາມ ແລະ SQL ຂອງມັນຈະຊີ້ນຳຄຳສອບຖາມສຳລັບຄຳຖາມທີ່ຄ້າຍກັນໃນພາຍຫຼັງ.

### ປ່ຽນຄຳຕອບເປັນແດຊບອດໄດ້ບໍ່?

ທຸກຄຳຕອບກັບມາພ້ອມຕາຕະລາງ ແລະ ກຣາຟທີ່ແພລດຟອມເລືອກຕາມຮູບແບບຂອງຜົນ, ແລະ ປັກໝຸດອັນໃດກໍໄດ້ໃສ່ບອດ. ບອດມີຫຼາຍແທັບ, ມີຕົວກັ່ນຕອງ ແລະ ຊ່ວງວັນທີຂອງຕົນເອງ, ແລະ ແບ່ງປັນໃຫ້ຄົນທີ່ຄວນເຫັນຕົວເລກໄດ້ ໂດຍບໍ່ຕ້ອງໃຫ້ສິດເຂົ້າຖານຂໍ້ມູນເບື້ອງຫຼັງ.

### ໃຜເຫັນຂໍ້ມູນໃດໄດ້?

ສິດເຂົ້າເຖິງກຳນົດຕໍ່ແຫຼ່ງຂໍ້ມູນ, ແລະ ບອດທີ່ແບ່ງປັນບໍ່ໄດ້ຕິດການເຊື່ອມຕໍ່ໄປນຳ — ຜູ້ເບິ່ງເຫັນບອດ ບໍ່ແມ່ນໜ້າຈໍສືບຄົ້ນ. ການເຊື່ອມຕໍ່ແບບອ່ານຢ່າງດຽວ, ການຈຳກັດແຖວໃນທຸກຄຳສັ່ງ, ແລະ ການບັນທຶກສິ່ງທີ່ຖືກຖາມ ແລະ ຄ່າໃຊ້ຈ່າຍໃນແຕ່ລະຄັ້ງ ມີຜົນທົ່ວທັງລະບົບ.

## ເຊື່ອມຕໍ່ຖານຂໍ້ມູນ ແລ້ວ ລອງຖາມມັນເບິ່ງ
