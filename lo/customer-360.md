# Customer 360 — ບັນທຶກດຽວ ຂ້າມທຸກຊ່ອງທາງ

## Customer 360 ທີ່ປະກອບຂຶ້ນ ຈາກສິ່ງທີ່ເກີດຂຶ້ນແລ້ວ

ການສົນທະນາຈາກທຸກຊ່ອງທາງ, ເບີໂທທີ່ຈັບໄດ້ໃນລະຫວ່າງການສົນທະນາ, ແລະ ຂໍ້ມູນສົດຈາກລະບົບຂອງທ່ານເອງ ມາລວມກັນເປັນມຸມມອງລູກຄ້າດຽວ — ອັນດຽວກັນທີ່ທີມຂອງທ່ານອ່ານ ແລະ ຕົວແທນຂອງທ່ານໃຊ້ຕອບ.

## ບັນທຶກສ້າງຕົວມັນເອງແນວໃດ

ບໍ່ຕ້ອງມີໂຄງການປ້ອນຂໍ້ມູນ. ໂປຣໄຟລ໌ມາຈາກການສົນທະນາທີ່ທ່ານມີຢູ່ແລ້ວ.

1. **ເຊື່ອມຕໍ່ຊ່ອງທາງຂອງທ່ານ** — ທຸກການສົນທະນາທີ່ກ່ອງຂໍ້ຄວາມຈັດການ ສ້າງບັນທຶກຂຶ້ນ: ໃຜທັກມາ, ຈາກບ່ອນໃດ, ເລື່ອງຫຍັງ. ບໍ່ຕ້ອງກອກຫຍັງເພີ່ມ — ໂປຣໄຟລ໌ມີຢູ່ ເພາະການສົນທະນາມີຢູ່.
2. **ເພີ່ມຂໍ້ມູນຂອງທ່ານເອງ** — ເຊື່ອມ endpoint ເສີມຂໍ້ມູນ, ນຳເຂົ້າສະເປຣດຊີດ ຫຼື ຊິງຈາກ API ພາຍໃນ. ຈາກນັ້ນເລືອກເທື່ອດຽວສຳລັບທັງ workspace ວ່າຈະສະແດງປະຫວັດໃນການສົນທະນາ, ໃນແຖບ Customer 360 ຫຼື ບໍ່ສະແດງເລີຍ.
3. **ເຮັດວຽກຈາກພາບລວມທັງໝົດ** — ທີມຂອງທ່ານຕອບໂດຍມີປະຫວັດຢູ່ຕໍ່ໜ້າ, ແລະ ຕົວແທນຂອງທ່ານຕອບດ້ວຍບໍລິບົດດຽວກັນ — ລວມທັງສ່ວນທີ່ຢູ່ໃນລະບົບຂອງທ່ານ ບໍ່ແມ່ນຂອງພວກເຮົາ.

## ໂປຣໄຟລ໌ທີ່ທັນສະໄໝສະເໝີ ເພາະມັນຖືກສ້າງຂຶ້ນເອງ

ບໍ່ແມ່ນຟອມທີ່ຕ້ອງມີຄົນຈື່ມາອັບເດດ.

### ຄົນດຽວ, ທຸກຊ່ອງທາງ

ເປີດການສົນທະນາ Messenger ແລ້ວຂໍ້ຄວາມຈາກແຊັດເວັບໄຊ ແລະ Zalo ຂອງຄົນດຽວກັນກໍຢູ່ໃນນັ້ນແລ້ວ, ເຊື່ອມກັນດ້ວຍເບີໂທ ຫຼື ອີເມວທີ່ໃຊ້ຮ່ວມກັນ. ບໍ່ມີຫຍັງຖືກເຊື່ອມເພາະຊື່ຄ້າຍກັນ — ຖ້າບໍ່ມີຕົວລະບຸຮ່ວມ, ສອງການສົນທະນາຈະແຍກກັນ ແທນທີ່ຈະຖືກເດົາລວມກັນ.

### ຂໍ້ມູນຕິດຕໍ່ ທີ່ທ່ານບໍ່ໄດ້ພິມເອງ

ເບີໂທທີ່ລູກຄ້າຂຽນລະຫວ່າງການສົນທະນາ ຈະຖືກກວດພົບ, ຕັດອັນຊ້ຳກັບທີ່ທ່ານມີແລ້ວ, ແລະ ຕິດໄວ້ກັບການສົນທະນາ — ເບີຂອງພະນັກງານ ແລະ ເບີໃນຂໍ້ຄວາມທີ່ອ້າງອີງ ຖືກຄັດອອກ ບໍ່ຖືກນັບ.

### ລະບົບຂອງທ່ານ ຢູ່ໃນແຜງ

ຊີ້ໄປຫາ endpoint ທີ່ທ່ານຄວບຄຸມ. ພວກເຮົາສົ່ງຕົວລະບຸທີ່ມີ; ລະບົບຂອງທ່ານຕອບກັບດ້ວຍລາຍການໄທມ໌ລາຍ — ຄຳສັ່ງຊື້, ການໂທ, ການເຂົ້າເວັບ — ສະແດງໃນການສົນທະນາ ຫຼື ໃນແຖບ Customer 360, ແລະ ບໍ່ຖືກກັອບປີ້ເຂົ້າຖານຂໍ້ມູນຂອງພວກເຮົາ ເວັ້ນເສຍແຕ່ທ່ານເປີດການແຄຊ.

### ບໍລິບົດທີ່ຕົວແທນຂອງທ່ານໃຊ້ໄດ້

ແຄຊແຫຼ່ງຂໍ້ມູນ ແລະ ເປີດບໍລິບົດພາຍນອກ, ຕົວແທນທີ່ຕອບຈະອ່ານຈາກແຄຊນັ້ນ — ຈຶ່ງຕອບເລື່ອງຄຳສັ່ງຊື້ໄດ້ ໂດຍບໍ່ຕ້ອງໃຫ້ API ພາຍໃນຂອງທ່ານຢູ່ໃນເສັ້ນທາງຂອງທຸກຂໍ້ຄວາມ.

### ນຳລູກຄ້າທີ່ທ່ານມີເຂົ້າມາ

ນຳເຂົ້າຈາກສະເປຣດຊີດ ດ້ວຍການຈັບຄູ່ຖັນທີ່ຈື່ໄວ້, ຫຼື ຊິງຈາກແຫຼ່ງ HTTP ແບບ cursor ເພື່ອໃຫ້ແຕ່ລະຮອບເລີ່ມຕໍ່ຈາກບ່ອນທີ່ຮອບກ່ອນຢຸດ. ແຕ່ລະແຖວອີງໃສ່ລະຫັດລູກຄ້າຂອງທ່ານເອງ, ການນຳເຂົ້າຄັ້ງຕໍ່ໄປຈຶ່ງອັບເດດ ແທນທີ່ຈະເພີ່ມອັນຊ້ຳ.

### ກວດສິດທີ່ຖານຂໍ້ມູນ ບໍ່ແມ່ນແຕ່ API

ບັນທຶກລູກຄ້າຄວບຄຸມໂດຍລະບົບສິດຂອງພື້ນທີ່ເຮັດວຽກ ແລະ ບັງຄັບໃຊ້ໃນລະດັບຖານຂໍ້ມູນ, ສະມາຊິກທີ່ບໍ່ມີສິດຈຶ່ງເຂົ້າເຖິງແຖວຂໍ້ມູນບໍ່ໄດ້ທຸກທາງ — ລວມທັງການສືບຄົ້ນໂດຍກົງ.

## Customer 360 ມີຫຍັງແດ່

ສິ່ງທີ່ມາເອງ, ສິ່ງທີ່ທ່ານນຳມາ, ແລະ ໃຜມີສິດເຫັນ.

### ຄຽງຂ້າງທຸກການສົນທະນາ

- ຂໍ້ຄວາມຂອງຄົນດຽວກັນຈາກຊ່ອງທາງອື່ນ
- ເບີໂທທີ່ກວດພົບ, ຄັດແລ້ວ
- ລູກຄ້າທີ່ເຊື່ອມໂຍງ ພ້ອມຄຳສັ່ງຊື້ຫຼ້າສຸດ
- ປ້າຍກຳກັບ, ບັນທຶກພາຍໃນ ແລະ ຄຸນລັກສະນະກຳນົດເອງ
- ບົດສະຫຼຸບການສົນທະນາແບບມີໂຄງສ້າງ

### ເສີມຂໍ້ມູນຈາກລະບົບຂອງທ່ານ

- HTTP endpoint ທີ່ທ່ານຄວບຄຸມ, GET ຫຼື POST
- ຕົວລະບຸທີ່ສົ່ງໄປ: ການສົນທະນາ, ຊ່ອງທາງ, external id, ເບີໂທ, ອີເມວ, ຊື່, ຄຸນລັກສະນະ
- ການສະແດງຜົນແບບດຽວສຳລັບ workspace: ໃນແຖວ, ແຜງ ຫຼື ເຊື່ອງ
- ຈຳກັດແຫຼ່ງໃຫ້ໃຊ້ກັບການສົນທະນາສ່ວນຕົວ ຫຼື ກຸ່ມ
- Auth header ເຂົ້າລະຫັດຂະນະຈັດເກັບ, ບໍ່ເຄີຍສົ່ງກັບໄປບຣາວເຊີ

### ການນຳລູກຄ້າເຂົ້າມາ

- ນຳເຂົ້າຈາກສະເປຣດຊີດ ພ້ອມຈື່ການຈັບຄູ່ຖັນ
- ແຫຼ່ງ HTTP ໃນໂໝດເຊື່ອມຕໍ່ ຫຼື ຊິງຄ໌
- ຊິງຄ໌ແບບ cursor ທີ່ສືບຕໍ່ຈາກບ່ອນທີ່ຢຸດ
- ປະຫວັດການຊິງຄ໌ ພ້ອມຈຳນວນ ແລະ ຂໍ້ຜິດພາດ
- Upsert ຕາມ external id ຂອງທ່ານ, ການນຳເຂົ້າຊ້ຳຈຶ່ງເປັນການອັບເດດ

### ສຳລັບຕົວແທນ

- ເລືອກເປີດບໍລິບົດພາຍນອກ ແຍກຕາມແຫຼ່ງ
- ດຶງຈາກແຄຊ, ບໍ່ຢູ່ໃນເສັ້ນທາງສຳຄັນຂອງການຕອບ
- ໜ່ວຍຄວາມຈຳທີ່ຕົວແທນເກັບໄວ້ກ່ຽວກັບລູກຄ້າ
- ເຄື່ອງມືທີ່ດຳເນີນການກັບບັນທຶກໄດ້

### ສຳລັບທີມຂອງທ່ານ

- ລາຍຊື່ລູກຄ້າ ພ້ອມການຄົ້ນຫາ ແລະ ຕົວກັ່ນຕອງ
- ໜ້າລາຍລະອຽດ ສຳລັບລູກຄ້າແຕ່ລະຄົນ
- ເຊື່ອມການສົນທະນາກັບລູກຄ້າ ຫຼື ສ້າງໃໝ່ ຈາກແຜງຂໍ້ມູນຕິດຕໍ່
- ຊ່ອງທາງອື່ນຂອງຄົນດຽວກັນ ຢູ່ໃນການສົນທະນາທີ່ທ່ານເປີດ

### ການຄວບຄຸມ

- ກວດສິດ, ບັງຄັບໃຊ້ທີ່ຖານຂໍ້ມູນ
- ສິດລະດັບຊ່ອງທາງຍັງໃຊ້ຢູ່: ປະຫວັດຈາກຊ່ອງທາງທີ່ພະນັກງານເປີດບໍ່ໄດ້ ຈະບໍ່ປາກົດໃນການສົນທະນາຂອງເຂົາ
- ຂໍ້ມູນພາຍນອກຖືກດຶງມາສະແດງ, ບໍ່ໄດ້ກັອບປີ້ແບບງຽບໆ
- ປິດແຫຼ່ງເສີມຂໍ້ມູນໄດ້ ໂດຍບໍ່ຕ້ອງລຶບ

## ຄຳຖາມກ່ຽວກັບ Customer 360

ສິ່ງທີ່ທີມຕ່າງໆຖາມ ກ່ອນເຊື່ອມລະບົບພາຍໃນເຂົ້າກັບມັນ.

### ອັນໃດເຮັດໃຫ້ມັນເປັນມຸມມອງ 360 ບໍ່ແມ່ນແຕ່ລາຍຊື່ຜູ້ຕິດຕໍ່?

ມັນຖືກປະກອບຂຶ້ນ ບໍ່ແມ່ນພິມໃສ່ເອງ, ແລະ ຢູ່ບ່ອນທີ່ທ່ານເຮັດວຽກ: ເປີດການສົນທະນາ ແລ້ວຂໍ້ຄວາມຂອງຄົນດຽວກັນຈາກຊ່ອງທາງອື່ນ — ຈັບຄູ່ດ້ວຍເບີໂທ ຫຼື ອີເມວຮ່ວມ — ກໍຢູ່ໃນການສົນທະນາແລ້ວ, ຄຽງຂ້າງເບີທີ່ກວດພົບໃນນັ້ນ, ລູກຄ້າທີ່ເຊື່ອມໂຍງພ້ອມຄຳສັ່ງຊື້ຫຼ້າສຸດ, ແລະ ສິ່ງທີ່ລະບົບຂອງທ່ານລາຍງານ. ມັນທັນສະໄໝເພາະຖືກອະນຸມານມາ ບໍ່ແມ່ນເພາະມີຄົນຈື່ອັບເດດ.

### ມັນສະແດງຂໍ້ມູນຈາກ CRM ຫຼື ລະບົບຄຳສັ່ງຊື້ຂອງພວກເຮົາເອງໄດ້ບໍ່?

ໄດ້. ທ່ານຊີ້ໄປຫາ HTTP endpoint ທີ່ທ່ານຄວບຄຸມ. ພວກເຮົາສົ່ງຕົວລະບຸທີ່ມີ — ການສົນທະນາ, ຊ່ອງທາງ, external id, ເບີໂທ, ອີເມວ, ຊື່, ຄຸນລັກສະນະກຳນົດເອງ — ແລະ endpoint ຂອງທ່ານຕອບກັບດ້ວຍລາຍການໄທມ໌ລາຍທີ່ມັນຮູ້ຈັກ: ຄຳສັ່ງຊື້, ການໂທ, ການເຂົ້າເວັບ. ໂດຍຄ່າເລີ່ມຕົ້ນ ບໍ່ມີຫຍັງຖືກກັອບປີ້ເຂົ້າຖານຂໍ້ມູນຂອງພວກເຮົາ; ມັນຖືກດຶງມາ ແລະ ສະແດງ. ແຫຼ່ງລູກຄ້າໃນໂໝດເຊື່ອມຕໍ່ ຍັງສະແດງຊື່, ເບີໂທ ແລະ ອີເມວຂອງຄົນນັ້ນໄດ້, ອ່ານສົດເມື່ອເປີດການສົນທະນາ.

### ຕົວແທນ AI ໃຊ້ຂໍ້ມູນພາຍນອກນັ້ນຕອນຕອບໄດ້ບໍ່?

ສະເພາະເມື່ອທ່ານເປີດສຳລັບແຫຼ່ງນັ້ນ ແລະ ເກັບສຳເນົາແຄຊໄວ້. ຕົວແທນອ່ານບໍລິບົດພາຍນອກຈາກແຄຊນັ້ນ ແທນທີ່ຈະໃຫ້ endpoint ຂອງທ່ານຕອບທຸກຂໍ້ຄວາມ — API ພາຍໃນທີ່ຊ້າ ຫຼື ຖືກຈຳກັດອັດຕາ ຈຶ່ງບໍ່ເຄີຍເຮັດໃຫ້ການຕອບລູກຄ້າຊ້າລົງ.

### ນຳເຂົ້າລູກຄ້າທີ່ພວກເຮົາມີຢູ່ແລ້ວໄດ້ບໍ່?

ໄດ້ — ຈາກສະເປຣດຊີດ ດ້ວຍການຈັບຄູ່ຖັນທີ່ຕັ້ງເທື່ອດຽວ ແລະ ຖືກຈື່ໄວ້, ຫຼື ຈາກແຫຼ່ງ HTTP ທີ່ຊິງແບບ cursor ເພື່ອໃຫ້ແຕ່ລະຮອບເລີ່ມຕໍ່ຈາກບ່ອນທີ່ຮອບກ່ອນຢຸດ. ແຕ່ລະແຖວອີງໃສ່ລະຫັດລູກຄ້າຂອງທ່ານເອງ, ການນຳເຂົ້າຄືນຈຶ່ງອັບເດດລູກຄ້າຄົນເດີມ ແທນທີ່ຈະເພີ່ມສຳເນົາທີສອງ.

### ໃຜເຫັນບັນທຶກລູກຄ້າໄດ້?

ຂໍ້ມູນລູກຄ້າຖືກຄວບຄຸມໂດຍລະບົບສິດຂອງ workspace, ແລະ ການກັ້ນນີ້ຖືກບັງຄັບໃຊ້ທັງທີ່ຖານຂໍ້ມູນ ແລະ API — ສະມາຊິກທີ່ບໍ່ມີສິດ ບໍ່ສາມາດອ່ານແຖວຂໍ້ມູນໄດ້ດ້ວຍທາງໃດກໍຕາມ. ສິດລະດັບຊ່ອງທາງຖືກໃຊ້ເພີ່ມເຕີມ: ປະຫວັດຈາກຊ່ອງທາງທີ່ພະນັກງານເປີດບໍ່ໄດ້ ຈະບໍ່ເຄີຍປາກົດໃນການສົນທະນາຂອງເຂົາ.

### ຈະເປັນແນວໃດ ເມື່ອຄົນດຽວກັນທັກມາຈາກສອງຊ່ອງທາງ?

ຂໍ້ຄວາມຈາກອີກຊ່ອງທາງໜຶ່ງຈະປາກົດໃນການສົນທະນາທີ່ທ່ານເປີດ, ຈັບຄູ່ດ້ວຍເບີໂທ ຫຼື ອີເມວຮ່ວມ, ໃນຂະນະທີ່ສອງການສົນທະນາຍັງແຍກກັນ. ບໍ່ມີຫຍັງຖືກເດົາຈາກຊື່ທີ່ຄ້າຍກັນ — ຖ້າບໍ່ມີຕົວລະບຸຮ່ວມ ພວກມັນຈະແຍກກັນ. ເມື່ອທ່ານເຊື່ອມການສົນທະນາກັບລູກຄ້າ, ການຈັບຄູ່ຈະອີງໃສ່ການເຊື່ອມນັ້ນແທນເບີໂທ. ຖ້າສອງຊ່ອງທາງແມ່ນບັນຊີດຽວກັນແທ້ໆ, ສາມາດລວມທັງຊ່ອງທາງເຂົ້າກັບອີກຊ່ອງທາງໜຶ່ງໄດ້.
