## เชื่อมต่อกับฐานข้อมูลที่คุณใช้อยู่แล้ว

รองรับหกเอนจิน ตั้งแต่ Postgres บนเซิร์ฟเวอร์ของคุณเองไปจนถึงโปรเจกต์ BigQuery เลือกประเภท วางข้อมูลรับรอง เลือกตาราง — การเชื่อมต่อจะถูกทดสอบก่อนบันทึก

- **PostgreSQL** — โฮสต์ พอร์ต 5432 โหมด SSL
- **MySQL** — โฮสต์ พอร์ต 3306 โหมด SSL
- **ClickHouse** — โฮสต์ พอร์ต HTTP 8123
- **Snowflake** — บัญชี warehouse และ schema
- **BigQuery** — คีย์ service account และ location
- **Redshift** — Endpoint ของคลัสเตอร์ พอร์ต 5439

- ข้อมูลรับรองถูกเข้ารหัสเมื่อจัดเก็บ และไม่ถูกส่งกลับไปยังเบราว์เซอร์
- โหมดอ่านอย่างเดียว: มีเพียง SELECT เท่านั้นที่เข้าถึงได้
- สร้างโมเดลเฉพาะตารางที่คุณเลือก

## จาก connection string สู่บอร์ด

การทำโมเดลคือร่างแรกที่คุณแก้ต่อได้ ไม่ใช่โปรเจกต์ที่ต้องนัดวันทำ

1. **เชื่อมฐานข้อมูล** — ชี้ไปที่ PostgreSQL, MySQL, Redshift, ClickHouse, Snowflake หรือ BigQuery ข้อมูลรับรองถูกเข้ารหัสขณะจัดเก็บ และตั้งการเชื่อมต่อเป็นแบบอ่านอย่างเดียวได้ เพื่อให้มีแค่ SELECT เท่านั้นที่เข้าถึงได้
2. **ปรับแต่งโมเดล** — ระบบอ่านโครงสร้างสคีมาแล้วสร้างร่างแรกของ cube, join และตัวชี้วัดให้ ซ่อนสิ่งที่ไม่ควรมีใครคิวรี เปลี่ยนชื่อที่มีแต่คนตั้งเท่านั้นที่เข้าใจ และเพิ่มตัวชี้วัดที่ธุรกิจของคุณรายงานจริง
3. **ถาม แล้วปักหมุด** — ถามคำถามด้วยภาษาธรรมดา ตรวจ SQL เบื้องหลังคำตอบ แล้วปักหมุดคำตอบที่ควรเก็บไว้ลงบอร์ดที่ทีมเปิดดูทุกเช้า

## วิเคราะห์ข้อมูลด้วยตัวเอง โดยไม่มีตัวเลขที่แต่งขึ้น

มีชั้นเชิงความหมาย (semantic layer) อยู่ใต้คำถาม คำตอบจึงสอดคล้องกันเสมอ

### ถามด้วยภาษาธรรมดา

พิมพ์คำถามแบบที่คุณถามเพื่อนร่วมงาน คำตอบกลับมาเป็นตารางและกราฟที่เหมาะกับรูปแบบของผลลัพธ์ — พร้อมคิวรีที่ใช้รัน ใครก็ตรวจวิธีคิดได้

### semantic model ไม่ใช่การเดา

ตัวชี้วัด มิติ และการ join ถูกกำหนดครั้งเดียวแล้วคอมไพล์เข้าไปในทุกคิวรี “รายได้” มีความหมายเดียวกันในทุกคำตอบ และคำถามที่โมเดลแสดงไม่ได้ ก็จะไม่แอบกลายเป็นการ join ที่มโนขึ้นมา

### คำถามที่ยืนยันแล้ว ยังคงถูกต้องเสมอ

บันทึกคำตอบที่คุณตรวจแล้วเป็นตัวอย่างที่ตรวจสอบแล้ว คำถามและ SQL ของคำตอบนั้นจะเข้าไปอยู่ในตัวอย่างที่โมเดลอ่านก่อนเขียนคิวรี คำถามที่คล้ายกันครั้งถัดไปจึงทำตามแบบที่คุณอนุมัติไว้

### บอร์ด ที่สร้างจากคำตอบ

ปักหมุดคำตอบใดก็ได้ลงบอร์ด บอร์ดมีได้หลายแท็บ มีตัวกรองร่วม และช่วงวันที่ที่ยังคงเป็นแบบสัมพัทธ์ — บอร์ดที่บันทึกไว้เป็น “7 วันล่าสุด” เดือนหน้าก็ยังหมายถึง 7 วันล่าสุด

### SQL Lab สำหรับที่เหลือ

บางคำถามพิมพ์เองเร็วกว่าอธิบาย เขียน SQL เองบน semantic model เดียวกัน บันทึกคิวรีที่ใช้บ่อย ทำกราฟจากผลลัพธ์ แล้วปักหมุดไปที่บอร์ด

### แชร์ตัวเลข ไม่ใช่ข้อมูลรับรอง

บอร์ดที่แชร์แสดงตัวเลขโดยไม่ส่งฐานข้อมูลเบื้องหลังไปด้วย สิทธิ์ให้แยกตามแหล่งข้อมูล และผู้ดูได้บอร์ด ไม่ใช่หน้าคิวรี

## เชื่อมกับอะไรได้บ้าง และคุณได้อะไร

ทุกอย่างที่ชั้นโมเดล บอร์ด และคอนโซล SQL รองรับจริง

### ฐานข้อมูลและ data warehouse

- PostgreSQL และ MySQL
- Redshift และ ClickHouse
- Snowflake และ BigQuery
- เลือกตารางตอนเชื่อมต่อ — โมเดลอ่านเฉพาะตารางเหล่านั้น

### ชั้นเชิงความหมาย

- Cube ที่สร้างจากสคีมาของคุณ แล้วปรับแต่งต่อ
- ตัวชี้วัดและมิติคำนวณที่คุณกำหนดเอง
- Join ที่ระบบแนะนำจากคีย์ และคุณเป็นคนยืนยัน
- Derived cube สำหรับรูปแบบที่เขียนด้วย SQL อย่างเดียวแล้วยุ่งเหยิง
- บริบทธุรกิจและคำศัพท์ที่โมเดลอ่าน

### บอร์ดและกราฟ

- หลายแท็บในบอร์ดเดียว
- ช่วงวันที่แบบสัมพัทธ์ที่ยังคงสัมพัทธ์
- ตัวกรองระดับบอร์ดที่ใช้กับทุกไทล์
- เลือกกราฟตามรูปแบบของผลลัพธ์
- แชร์ด้วยลิงก์ โดยไม่เปิดเผยแหล่งข้อมูล

### สำหรับคนที่เขียน SQL

- SQL Lab บนการเชื่อมต่อเดียวกัน
- คู่คำถามและ SQL ที่ผ่านการยืนยันแล้ว
- ขอบเขตตาราง — สิ่งที่โมเดลเห็นได้และเห็นไม่ได้
- บังคับจำกัดจำนวนแถวในทุกคิวรี
- รีเฟรชสคีมาเมื่อ data warehouse เปลี่ยน

### เอเจนต์ของคุณใช้ได้ด้วย

- เอเจนต์คิวรี semantic model เดียวกันได้
- คำตอบส่งไปที่แชท กล่องข้อความ หรือรายงานตามตารางเวลา
- MCP endpoint สำหรับไคลเอนต์ภายนอก
- บันทึกคำถาม คิวรี และต้นทุนของแต่ละรอบ

### การควบคุม

- ให้สิทธิ์แยกตามแหล่งข้อมูล
- การเชื่อมต่อแบบอ่านอย่างเดียว
- ข้อมูลรับรองเข้ารหัสขณะจัดเก็บ และไม่ถูกส่งกลับไปที่เบราว์เซอร์
- แชร์บอร์ดได้โดยไม่ส่งการเชื่อมต่อไปด้วย

## คำถามเกี่ยวกับการถามข้อมูล

สิ่งที่ทีมข้อมูลตรวจสอบก่อนจะเชื่อมกับระบบโปรดักชัน

### เชื่อมฐานข้อมูลและ data warehouse อะไรได้บ้าง?

PostgreSQL, MySQL, Redshift, ClickHouse, Snowflake และ BigQuery การเชื่อมต่อตั้งเป็นแบบอ่านอย่างเดียวได้ เพื่อให้มีแค่ SELECT เท่านั้นที่เข้าถึงได้ และข้อมูลรับรองถูกเข้ารหัสขณะจัดเก็บ และไม่ถูกส่งกลับไปที่เบราว์เซอร์

### ต่างจากการให้ LLM เขียน SQL ดิบอย่างไร?

โมเดลที่เดาจากชื่อตารางดิบพร้อมจะ join ผิดคอลัมน์ แล้วยื่นตัวเลขที่ผิดให้คุณอย่างมั่นใจ ที่นี่คำถามรันบน semantic model: คุณกำหนดตัวชี้วัด มิติ และการ join ครั้งเดียว และทุกคำตอบคอมไพล์จากนิยามเหล่านั้น “รายได้” มีความหมายเดียวกันในทุกกราฟ และคำถามที่แสดงผ่านโมเดลไม่ได้ ก็จะไม่แอบกลายเป็นคิวรีที่แต่งขึ้นมา

### ต้องทำโมเดลทุกอย่างก่อนถึงจะได้คำตอบไหม?

ไม่ต้อง ระบบอ่านโครงสร้างสคีมาตอนเชื่อมต่อ และสร้างร่างแรกของ cube, join และตัวชี้วัดให้ จากนั้นคุณปรับแต่ง — ซ่อนตารางที่ไม่ควรมีใครคิวรี เปลี่ยนชื่อคอลัมน์ที่มีแต่คนสร้างเท่านั้นที่เข้าใจ และเพิ่มตัวชี้วัดที่ธุรกิจของคุณรายงานจริง

### ยังเขียน SQL เองได้ไหมเมื่อจำเป็น?

ได้ SQL Lab รัน SQL ที่คุณเขียนเองบนการเชื่อมต่อและ semantic model เดียวกัน — บันทึกคิวรีที่ใช้บ่อย ทำกราฟจากผลลัพธ์แล้วปักหมุดไปที่บอร์ด หรือเปลี่ยนคิวรีเป็น derived cube ส่วนตัวอย่างที่ตรวจสอบแล้วมาจาก ChatQL เอง: บันทึกคำตอบที่คุณเชื่อถือ แล้วคำถามและ SQL ของคำตอบนั้นจะเป็นแนวทางให้คิวรีของคำถามที่คล้ายกันในภายหลัง

### เปลี่ยนคำตอบเป็นแดชบอร์ดได้ไหม?

ทุกคำตอบกลับมาพร้อมตารางและกราฟที่แพลตฟอร์มเลือกตามรูปแบบของผลลัพธ์ และปักหมุดลงบอร์ดได้ทุกอัน บอร์ดมีได้หลายแท็บ มีตัวกรองและช่วงวันที่ของตัวเอง และแชร์ให้คนที่ควรเห็นตัวเลขได้ โดยไม่ต้องให้สิทธิ์เข้าฐานข้อมูลเบื้องหลัง

### ใครเห็นข้อมูลอะไรได้บ้าง?

สิทธิ์ให้แยกตามแหล่งข้อมูล และบอร์ดที่แชร์ไม่ได้ส่งการเชื่อมต่อไปด้วย — ผู้ดูเห็นบอร์ด ไม่ใช่หน้าคิวรี การเชื่อมต่อแบบอ่านอย่างเดียว การจำกัดจำนวนแถวในทุกคิวรี และการบันทึกว่าถามอะไรและเสียค่าใช้จ่ายเท่าไหร่ในแต่ละรอบ มีผลกับทุกส่วน
